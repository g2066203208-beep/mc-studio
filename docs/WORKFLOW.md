# 开发与交付流程

## 需求到实现

1. 从玩家描述中提取目标玩法、当前行为和验收场景。
2. 核实 MC / NeoForge / Java / 相关 Mod 版本，读取对应源码分支。
3. 选择最小适用方案：配置、资源包、数据包、KubeJS、自有附属 Mod，或上游修复。
4. 开发在独立工程完成，适时提交。新功能必须有明确可观察的验收结果。
5. 构建后进行与改动相关的验证，输出 JAR、变更说明、已知限制与回滚方案。

## 测试分层

| 层次 | 需要的证据 |
|---|---|
| 编译和打包 | Gradle 退出码、构建日志、产物及 SHA-256 |
| 逻辑与数据 | 有价值的单元测试、数据生成检查或 GameTest；没有测试不能写“测试全过” |
| 最小客户端 | 成功加载 Mod、进入临时世界、完成验收操作、日志无相关异常 |
| 专用服务器 | 涉及共用逻辑或联网时检查服务端类加载、网络同步与加入世界 |
| 整合包 | 独立副本中验证依赖、Mixin、配方、资源和配置冲突 |
| 稳定性 | 按改动验证保存重载、区块切换、维度切换、退出重进 |
| 性能 | 相同场景与设置下对比帧时间、MSPT/TPS、内存或采样结果 |

服务器启动前遵守 Minecraft EULA 接受流程，不替用户伪造接受记录。缺少运行环境或交互能力时如实记录限制。

## 部署和回滚

- 开发运行目录、整合包测试实例、正式游玩实例分离。
- 先读取 HMCL 隔离设置或实际启动日志，确认生效 mods/config/saves 路径。
- 游戏退出后备份受影响的旧 JAR、配置和存档，记录版本、路径及哈希。
- 替换自己的目标 JAR，避免新旧两个版本同时存在；不批量清空 mods。
- 新版本确认通过后再移入游玩实例。涉及世界格式或注册内容的更新保留完整旧存档。
- 回滚恢复原 JAR、配置与匹配的存档快照，不能假定降级 JAR 就能恢复世界。

## GitHub 工作室

建议建立独立私有仓库 `mc-studio`，准备好源码授权和发布资料后再决定是否公开。
专用私有仓库为 https://github.com/g2066203208-beep/mc-studio；远程写入使用 GitHub 插件，本地 gh 尚未登录。
现有仓库不自动作为 MC 工作室使用。

- `main`：经验证的稳定提交。
- `feat/<主题>`、`fix/<主题>`、`upgrade/<版本>`：独立变更。
- 提交信息描述实际改动；提交前检查暂存区，禁止夹带账号和世界文件。
- PR 说明问题、行为变化、兼容版本、验证结果和风险。
- CI 用 Java 21 和工程 Wrapper 执行 build，保留 JAR；运行时兼容验证单独记录。
- 发布前核实所有第三方代码/素材许可，附兼容矩阵、依赖、更新说明和 SHA-256。
- 向第三方项目发 Issue/评论等对外沟通，需要用户明确指示。
